# FRP-ALL-IN-ONE v3.2.13

本版本修复两台设备均名为 `ubuntu`、隧道均名为 `SSH` 时争用全局代理名，导致关闭后重新启用持续报 `proxy [ubuntu.SSH] already exists` 的问题。同时完善客户端的连接恢复与配置应用成功确认。

## 核心修复

### 同名设备与同名隧道不再冲突

- FRPS 内部代理名由 `设备显示名.隧道显示名` 改为 `client-<完整设备 ID>.tunnel-<隧道 ID>`。
- **主机名和隧道显示名允许重复**：两台设备仍可都显示为 `ubuntu`，隧道仍可都叫 `SSH`，不需要用户改名。
- 同一设备内不同隧道也使用各自的唯一 ID，不因显示名称相同而冲突。
- 重命名、关闭和重新启用均保留稳定的内部标识；一台设备不再抢占另一台设备的同名代理。
- 不强制删除其他客户端的代理，不需要删除设备记录、清空数据库或重装客户端。

此次现场根因是代理重名，不是防火墙未开放或客户端管理连接离线。显示名可重复，但两个独立隧道仍不能同时独占同一协议、同一监听地址及同一对外端口。

### “配置应用成功”等待真实认证与注册

- 原有成功日志只表示配置已保存、新核心已创建，不代表 FRPS 认证或隧道注册成功。
- 管理配置应用现在等待 FRPS 认证连接与所有启用代理注册完成，再输出“配置应用成功：FRPS 已连接，启用隧道已注册”。
- 最多等待 45 秒，覆盖 FRP 默认的 30 秒代理注册重试间隔。未就绪时报告具体代理、状态或内核退出原因，不再把注册失败当成成功。
- 就绪超时保留目标配置与正在重试的核心，不悄悄恢复成关闭状态；收到相同配置仍检查就绪情况，但不无意义地重启工作中的核心。
- 代理注册成功不等同于目标 IP/端口可达；面板设备在线也仍不代表端到端业务连通。

### 瞬时连接失败后持续重试

- Agent 托管的 FRPC 核心统一使用持续登录重试，避免重载后首次连接失败就退出、但管理连接仍在线的状态。
- 对已有配置文件中的 `loginFailExit=true` 同样生效；仅改变本项目嵌入式 Agent 的运行策略，不修改独立 FRPC CLI 的默认行为。
- 该健壮性修复与此次已确认的代理重名根因分开处理。

## 升级与迁移

1. **先升级服务端到 v3.2.13。** 重名修复位于服务端配置生成；现有 v3.2.11 Agent 可以接收新的内部代理名，无需先删除或重新添加设备。
2. 服务端升级后，客户端管理连接重连注册时会自动获取最新权威配置。确认两台设备日志中的代理名分别包含各自的设备 ID，而不再共用 `ubuntu.SSH`。
3. 建议随后将客户端升级到 v3.2.13，以获得持续重连和准确的配置应用结果日志；仅升级客户端不能修复旧服务端继续生成重复代理名的问题。
4. 支持容器自升级的客户端可通过面板更新；旧安装或缺少 Docker Socket 的情况使用面板生成的客户端专属宿主机升级命令。保留原设备 ID、认证信息、数据卷和隧道配置。
5. FRPS 日志/API 中的内部代理名会变化，依赖旧代理名的外部工具应相应调整；页面中的原显示名称保持不变。

服务端宿主机升级命令：

```bash
curl -fsSL https://raw.githubusercontent.com/newbietan/FRP-ALL-IN-ONE/v3.2.13/deploy/upgrade.sh -o /tmp/frp-upgrade.sh
sudo bash /tmp/frp-upgrade.sh v3.2.13
```

不要使用 `deploy.sh` 代替已有服务的升级脚本，也不要先删除旧容器、数据库或设备。升级切换及客户端配置重载期间连接可能短暂中断，当前仍是重建内嵌 FRPC，并非零停机热更新；同一设备上的其他隧道也可能受到短暂影响。

详见 [隧道启停故障排查](https://github.com/newbietan/FRP-ALL-IN-ONE/blob/v3.2.13/docs/troubleshooting-tunnels.md) 与 [升级说明](https://github.com/newbietan/FRP-ALL-IN-ONE/blob/v3.2.13/docs/upgrade.md)。

## 回归验证

- 后端新增跨设备同名、同设备隧道同名、重命名及启停标识稳定测试；修复前复现失败，修复后通过。
- 使用真实 FRPS/FRPC 复现 `ubuntu.SSH already exists`，验证两种旧配置迁移顺序及两设备分别启停后的真实转发与路由隔离。
- 单设备连续五轮启停、首次连接瞬时失败恢复、端口注册失败、异步核心退出、就绪等待及相同配置重试测试通过。
- 本地全量 Agent 竞态测试、`go vet`、后端测试、前端测试与类型检查通过；真实 Docker 升级/回滚测试由隔离 CI 执行。
