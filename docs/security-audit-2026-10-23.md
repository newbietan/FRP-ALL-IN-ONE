## 结论

**原版本存在已确认的严重漏洞，不建议原样暴露公网。** 最严重的问题是未认证的静态文件路径穿越：在镜像默认静态资源目录存在时，可以读取应用进程有权限访问的任意普通文件，包括 SQLite 数据库与持久化 JWT 密钥。已在隔离环境用假数据复现“文件读取 → JWT 伪造 → 管理员 API 访问”的完整链条。

相关入口现已修复并通过回归测试。另已收紧首次管理员注册、OAuth、安装凭据权限、传输安全和 Docker Socket 默认权限，并更新依赖。**这不是对未来或所有部署条件下“绝无漏洞”的保证。** 剩余风险和未覆盖项目见后文。

## 范围与方法

审查了 FastAPI 路由与依赖、GitHub OAuth/JWT、三类 WebSocket、设备/隧道配置生成、安装和升级脚本、容器事务升级器、Go Agent、FRP 配置校验和 Unix Socket 插件、前端 Token 流程、Docker/Compose 与发布 CI。

- 应用层敏感路径：手工追踪认证、授权、文件系统、命令参数及网络信任边界。
- 定制 FRP 内核：重点审查配置、认证和插件路径，并运行核心单元测试与依赖可达性扫描；并非逐行验证全部上游内核。
- 依赖：npm audit、pip-audit、OSV 版本查询与 govulncheck。
- 凭据：对当前跟踪文件，以及非浅克隆历史中的 314 个提交、193,744 行历史差异执行有限规则扫描，未匹配到所扫描类型的真实硬编码凭据。规则覆盖私钥标记、常见 GitHub/AWS Token 和部分敏感配置字面量；不保证发现所有格式或编码后的密钥。
- 验证：临时目录、假密钥、假 GitHub 身份、内存数据库/临时 SQLite、ASGI 测试客户端。没有读取线上数据，没有对外部系统实施漏洞利用，也没有执行 Docker 宿主机接管操作。

### S-01：静态路由路径穿越，CWE-22 / CWE-200

原始位置：`server/main.py:618-634`，`serve_spa_frontend`。

原逻辑直接使用 `_static_dir / full_path`，只判断文件是否存在，然后交给 `FileResponse`。URL 解码后的 `..` 路径可以逃出静态目录；绝对路径还会覆盖原始目录前缀。这里既没有管理员依赖，也没有边界检查。

隔离验证结果：

| 假数据验证 | 修复前 | 修复后 |
| --- | --- | --- |
| 编码路径读取假 `.jwt_secret` | 200，可读 | 404 |
| 编码路径读取假 SQLite 数据库 | 200，可读 | 404 |
| 编码绝对路径读取假私有文件 | 200，可读 | 404 |
| 用读取到的假密钥伪造管理员 JWT | 管理 API 返回 200 | 无法再取得密钥；错误密钥 Token 返回 401 |
| 合法管理员 Token | 200 | 200 |

修复位置：`server/main.py:624-649`。拒绝绝对路径、父目录和隐藏路径；规范化后检查目标必须仍在静态目录内，同时拒绝逃逸符号链接及逃逸的 SPA 首页链接。正常静态文件及 SPA 路由保留。

**影响不局限于文件本身。** 数据库含设备凭据、系统配置等；默认镜像以 root 运行，Linux 下进程环境等普通文件也可能处于可读范围。环境变量方式配置 JWT 密钥不能代替修复文件读取漏洞。

### S-02：首次管理员抢占，CWE-862

原始位置：`server/routers/auth.py:142-256` 的首次注册分支；`deploy/deploy.sh` 原先允许跳过管理员限制。

已存在管理员、或已经正确指定初始 GitHub ID/用户名的部署，不属于“任意首登者抢占”的前提。不能把这个问题描述成任意现有账号认证绕过。

现首次注册必须配置 `INITIAL_ADMIN_GITHUB_ID` 或 `INITIAL_ADMIN_GITHUB_USERNAME`，否则返回 503 且不创建管理员；同时配置时仅以数字 ID 为准。一键部署不再允许跳过身份配置。

### S-03 / S-04：明文管理通道与宿主机权限放大

证据包括原 `server/run.sh` / `server/Dockerfile` 的公网 HTTP 监听、生成脚本的 `ws://` 地址、Agent 对明文地址的默认接受，以及 `deploy/compose.yml` 和客户端脚本中的 Socket 挂载。

FRP 内核的 `unix_domain_socket` 插件支持连接指定 Unix Socket：

- `core/frp_custom/pkg/plugin/client/unix_domain_socket.go`
- `core/frp_custom/pkg/config/v1/validation/plugin.go` 的 `validateUnixDomainSocketPluginOptions`

当攻击者已控制管理员配置推送能力或明文管理连接时，Socket 挂载会把客户端内的配置能力放大到容器引擎控制面。此链条的配置能力、插件行为与挂载条件已确认；未实际执行创建特权容器或修改宿主机的利用。

现采取的边界：

- `server/run.sh` 默认仅监听回环，支持可信 HTTPS 代理或显式原生 TLS，限制 WebSocket 单消息为 1 MiB。
- `server/core/security.py` 校验凭据传输与公开 URL；不直接信任用户提供的 X-Forwarded-Host、X-Forwarded-Proto 或 Origin。
- HTTP 凭据端点、服务端 WebSocket 和 Agent 默认拒绝公网明文管理。
- Agent 保持正常证书验证，不以跳过验证解决 TLS 证书问题。
- 新 Compose 和新客户端不默认挂载 Socket；远程升级需管理员显式选用。
- `FRP_ALLOW_INSECURE_HTTP=1` 是明确的危险迁移开关，不应作为生产修复方案。

旧容器挂载和旧 Agent 地址不会被工作区代码自动改变，必须人工迁移。

### S-05：安装能力越界到已有设备凭据

原始位置：`server/routers/frp_server.py:395-463`。有效安装密钥加已有 `client_id` 可返回含旧 `auth_token` 的安装脚本。`client_id` 不是凭据，但长期通用安装密钥也不应自动成为所有旧设备的凭据读取权限。

现 `_serve_agent_install_script` 对已有设备要求管理员或专用、短期、单次升级凭据；安装密钥只能创建新设备。复测旧设备请求返回 403，新设备正常注册，升级凭据原有单次和客户端绑定测试保持通过。

### S-06：OAuth 流程状态与 URL 凭据

原 `github_callback` 在缺少 state 时仍交换授权码，普通 state 仅验证 JWT 签名，未检查用途或绑定浏览器。GitHub 用户身份仍由 GitHub 返回，**不能仅凭缺省 state 伪造任意已绑定管理员的 GitHub 身份**；其主要问题是 OAuth 流程混淆和 CSRF 防护缺失。

现使用受容量限制的短期随机 state、HttpOnly/SameSite 浏览器 Cookie、过期检查和单次消费；回调使用登录发起时保存的可信公开地址。换绑改为 Bearer 鉴权 POST，不再在换绑 URL 中传管理员 JWT。跨用途 JWT、缺少/错配 Cookie、过期和重放均被测试拒绝。

### S-07：依赖与构建供应链

- npm 初次扫描：6 个依赖分组，5 high、1 moderate，包含 Vite、PostCSS、Browserslist、nanoid 等。修复锁文件后为 0；Vite 从 6.4.3 更新到 6.4.5，未使用强制跨主版本升级。
- 原 Python 浮动范围可解析到带公告的 python-jose/ecdsa。原应用固定 HS256，不等同于已证明存在公告中的非对称密钥混淆攻击。仍迁移到 PyJWT，去除相关依赖，并用带哈希的生产锁文件构建。
- Go：gorilla/websocket 更新为 1.5.3，x/net 更新为 0.60.0，并同步依赖；Go 最低补丁为 1.26.9，镜像/CI 使用已验证存在的 1.26.10。
- Agent 基础镜像由 Alpine 3.20 更新为 3.23。
- 移除 Python 安装时的 `trusted-host` TLS 绕过与旧 pip 降级，镜像安装启用 `--require-hashes`。

## 尚存风险与建议

1. **WebSocket URL 仍携带管理员 Token**：浏览器 API 的现有机制使用查询参数，可能被代理/访问日志记录。建议后续改为短期、单次、用途绑定的 WebSocket 票据，并对日志作查询参数脱敏；当前必须限制日志访问，不应把日志当作无敏感信息的数据分享。
2. **安装密钥仍是高权限长期能力**：虽然已不能读取旧设备凭据，但仍可注册新设备并取得 FRPS 接入配置。不要公开或跨租户分发，泄露后立即轮换；建议增加一次性注册票据和配额。
3. **已被攻陷的 Agent 仍可滥用上报**：单消息大小已限制，但指标键名、数值及总缓存/广播预算仍需进一步白名单化和按设备限流。不要将控制面与不可信多租户设备置于同一信任域。
4. **共享 FRPS Token 与允许端口范围**：当前不是多租户隔离系统；丢失单设备上的共享 FRPS 凭据可能扩大影响。建议结合独立身份、认证插件、受限端口范围和网络分段。
5. **镜像、安装脚本与发布链仍需更强的真实性保证**：固定版本及本地 image ID 不是发布签名。建议实施签名验证、镜像摘要固定、Actions 提交 SHA 固定、SBOM 与持续镜像扫描。仓库/镜像发布账号失陷不在本次代码修改可独立解决的范围内。
6. **TLS 运维和旧安装权限**：当前默认单容器不应依赖遗留 TLS 管理器自动配置 HTTPS；按 [安全部署指南](security.md) 配置外部代理或原生 TLS，撤销旧 Socket 挂载并轮换凭据。
7. **部署在共享主机时继续做最小权限加固**：限制数据卷和日志的本机读取权限，评估非 root、能力裁剪、专用管理网络及备份加密。

## 限制及发布前检查

- 本机没有 Docker 引擎和 PowerShell；2 个真实 Docker 事务测试及 1 个 PowerShell 解析测试被明确跳过。没有构建/运行最终容器镜像，也没有执行容器操作系统包漏洞扫描。
- Go 测试主要运行于本机 darwin/arm64；未跑真实多机 NAT/公网 FRP e2e，也未把本地测试视为 Windows/Linux 实机验证。
- GitHub OAuth 使用假响应验证安全逻辑，未用真实账号执行登录/换绑；发布前应在受控 HTTPS 环境进行真实 OAuth 与 Cookie 行为验收。
- state 暂存为进程内缓存，适用于当前默认单 worker；若改为多 worker/多副本，应使用共享、原子消费的状态存储或可靠会话路由，否则可能登录失败。
- 本次未自动发布新镜像，也未更改线上数据库、撤销已泄露 Token 或替用户配置证书/防火墙。

**上线前必须执行 [安全部署与泄露响应步骤](security.md#旧版本迁移与泄露响应)。如果旧版本曾暴露公网，更新代码不能代替密钥轮换和历史入侵排查。**
